# Архитектура

Сервис — «цифровой секретарь»: фото документа → текст (OCR) → карточка полей → ответ со ссылкой на пункт Положения. Ниже — как это разложено по слоям, куда класть новый код и чем это защищено от развала.

## Слои

Зависимости идут только сверху вниз: модуль может импортировать свой слой и нижележащие, но не вышележащие. Это проверяет [`tests/test_architecture.py`](../tests/test_architecture.py) — тест читает исходники и падает при нарушении.

```
 tools        cli · evaluate · official · synth          запуск, оценка, выгрузка results.json, генератор данных
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 adapters     web · telegram · admin                     транспорт: HTTP-сайт, Telegram-бот, кабинет сотрудника
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 services     assistant · dialog · storage ·             сценарии и состояние: анкета, документ сессии, DOCX,
              templates · accounts · mailer · doctypes   обращения, SQLite, аккаунты, управление типами документов
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 pipeline     pipeline · export                          один конвейер: файл → OCR → тип → поля → ответ → JSON
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 knowledge    kb · knowledge_base · qa · llm             Положение, поиск (BM25 + синонимы), ответы, локальная модель
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 document     ocr · extract · classify ·                 чтение документа: снимок, текст, поля, подпись и печать
              document_processing · highlight
 ─────────────────────────────────────────────────────────────────────────────────────────────────────────────
 foundation   models · config · textutil                 общие типы, конфигурация, работа с русским текстом
```

Правила, которые держит тест:

* **Нижний слой не знает про верхний.** OCR не знает про базу знаний, база знаний — про сайт, ядро — про Telegram.
* **Адаптеры не зависят друг от друга.** Бот и сайт работают с общим ядром `assistant/`, а не друг с другом: анкета, начатая в боте, продолжается на сайте именно потому, что обе стороны вызывают один и тот же `AssistantCore`. Подключает их вместе только `web/app.py` (корень сборки).
* **HTTP-фреймворк живёт только в `web/` и `admin/`.** Ядро и бот его не импортируют; ошибки сценария — `assistant.ServiceError` (текст для человека и код, который сайт отдаёт как HTTP-статус).
* **Циклов между пакетами нет.**
* Каждый новый пакет или модуль верхнего уровня нужно отнести к слою (тест напомнит).

## Путь одной проверки

```
файл + вопрос
  └─ web (POST /api/jobs) или telegram (фото в чат)            адаптер принимает и отдаёт, ничего не решает
       └─ assistant.AssistantCore / pipeline.Dekanat.analyze   ядро и конвейер
            ├─ ocr.OcrRunner         выпрямление, тени, блики, перебор вариантов → слова с рамками
            │    └─ ocr.photo        оценка снимка: размытие, темнота, блики, мелкий текст → совет переснять
            ├─ classify              тип документа: автоматически или выбран вручную
            ├─ extract               карточка полей по описанию типа (config/doc_types/*.yaml) + подпись и печать по изображению
            ├─ document_processing   проверка формата файла и значений полей
            ├─ kb + qa               какие пункты Положения относятся к документу и вопросу → вердикт и источники
            └─ llm (по переключателю) дозаполнение полей и пересказ; по умолчанию выключено
```

## Куда добавлять новое

| Задача | Где |
|---|---|
| Новый тип документа | описание в `config/doc_types/<тип>.yaml` или в кабинете сотрудника («Типы документов»); код не меняется. Общая логика проверки, записи и отката — `doctypes.DocTypeManager` |
| Другое Положение | замена файла в `data/regulations/` или загрузка в кабинете («База знаний») |
| Новый канал (чат другого мессенджера, почта) | новый пакет-адаптер рядом с `telegram/`: принимает сообщения и вызывает `assistant.AssistantCore`; в `web/app.py` подключается рядом с ботом. Импортировать `web` и `fastapi` ему не нужно |
| Новый шаг конвейера | в `pipeline.Dekanat.analyze`; сам шаг — в пакете слоя `document` или `knowledge` |
| Новый формат выгрузки результатов | модуль в `tools` (как `official.py`): читает результат `pipeline`, ничего не добавляя в нижние слои |

## Данные и состояние

* **SQLite** (`storage/`): сессии, обращения, статистика событий без текстов, журнал действий администратора, шаблоны, аккаунты и очередь уведомлений. Снимки и PDF на диск и в базу не пишутся.
* **Файлы конфигурации**: `config/settings.yaml` (любой параметр — переменной окружения `DEKANAT_<РАЗДЕЛ>_<КЛЮЧ>`), `config/doc_types/*.yaml`, `config/synonyms.yaml`.
* **Кэш в памяти процесса**: последние распознанные документы (`ocr.cache_size`), чтобы уточняющий вопрос по тому же файлу не запускал OCR заново.

## Что здесь решено сознательно

* **Правила по умолчанию, модель по переключателю.** Всё работает на правилах Python; локальная модель (`USE_LOCAL_LLM`) только дозаполняет поля и пересказывает ответ, а её выводы проверяет код (номер пункта принимается только из найденных).
* **Внешние API не используются.** Telegram — только транспорт: распознавание и ответы считаются на нашем сервере.
* **Оценка снимка — совет, а не запрет.** `ocr.photo` никогда не блокирует проверку: если текст всё равно прочитан уверенно, замечаний нет; если нет — совет переснять приходит вместе с ответом, а при выборе файла — коротким предупреждением (`POST /api/quality`, без OCR).
