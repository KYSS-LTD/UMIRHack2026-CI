# Онлайн-деканат — цифровой секретарь

Студент присылает **фото справки или заявления** и задаёт вопрос. Сервис **читает документ (OCR)**, **заполняет карточку полей**, **отвечает по Положению со ссылкой на пункт** и показывает, где на снимке найдено каждое поле. Если ответа нет ни в документе, ни в Положении — честно говорит об этом.

```
загрузка файла (фото / скан / PDF) + вопрос на русском
   │
   ├─ проверка формата: только JPG, JPEG, PNG, PDF (по содержимому файла); пустые, повреждённые и слишком большие — понятная ошибка
   ├─ OCR (Tesseract, rus+eng): поиск листа, выпрямление наклона до ±45°, тень, блики   ← внешние API не используются, всё на CPU
   ├─ определение типа документа: автоматически или выбор вручную
   ├─ извлечение полей по схеме типа (метки → шаблоны → запасные детекторы; подпись и печать — по изображению)
   ├─ валидация: у каждого поля статус обнаружения, исходный фрагмент, уверенность и причина сомнения
   ├─ поиск по Положению: какие пункты относятся к документу и вопросу (BM25 + синонимы, без языковой модели)
   └─ ответ с источниками: «в порядке» / «не хватает …» / «ответа нет» + пункт Положения или поле документа + оговорка о деканате
```

Три вида ответов — как в ТЗ:

| Вердикт | Пример ответа |
|---|---|
| **Документ в порядке** | «Справка содержит все данные, которые требует п. 3.2 Положения. Окончательное решение примет сотрудник деканата.» |
| **Чего-то не хватает** | «Не хватает даты выдачи и печати вуза. Эти поля обязательны по п. 3.4 Положения.» |
| **Ответа нет** | «В документе и в Положении нет информации по вопросу «Сколько стоит обучение?». Обратитесь в деканат.» |

> Для работы нужны **только Python и Tesseract**. Никаких облачных сервисов, ключей и скачивания моделей при запуске. Языковая модель по умолчанию **выключена** (`USE_LOCAL_LLM=false`): всё работает на правилах Python. Локальная Qwen2.5-3B-Instruct на CPU — необязательное дополнение (см. «Гибридный режим»).

Сервис **не принимает административных решений**: он даёт обоснованную предварительную оценку со ссылкой на пункт Положения или поле документа, а окончательное решение о переводе, зачислении или соответствии документа остаётся за сотрудником деканата. Эта оговорка есть в каждом ответе (`answer.report.disclaimer`).

## Что сделано по ТЗ

**Базовый уровень (обязательно)**

| № | Требование | Где и как |
|---|---|---|
| 1 | Принять документ и вопрос (JPG, PNG, PDF; вопрос на русском) | веб-страница, `POST /api/analyze`, CLI `ask` / `batch`; PDF — до 5 страниц |
| 2 | Распознать текст с помощью OCR | Tesseract 5 (`dekanat/ocr/`) |
| 3 | Заполнить карточку полей выбранного типа; нет поля — «не найдено» | `dekanat/extract/`, типы описаны в `config/doc_types/*.yaml` |
| 4 | Ответить по полям документа и пунктам Положения | `dekanat/qa/`, `dekanat/kb/` |
| 5 | Указать источник: номер пункта или поле документа | у каждого ответа `sources` (пункт Положения / поле + рамка на снимке) |
| 6 | Не выдумывать | ответ собирается только из найденных полей и дословного текста пунктов; нет данных → «ответа нет» |

Тип документа можно выбрать вручную (или оставить автоопределение). Интерфейс — веб-страница.

Три вида ответов из ТЗ воспроизводятся дословно (это проверяют тесты `tests/test_qa.py`): «Справка содержит все данные, которые требует п. 3.2 Положения. Окончательное решение примет сотрудник деканата», «Не хватает даты выдачи и печати вуза. Эти поля обязательны по п. 3.4 Положения», «В документе и в Положении нет информации о стоимости обучения. Обратитесь в деканат». Для частых тем вне Положения (стоимость, стипендия, общежитие, сессия, проходные баллы) ответ называет тему, для остальных — сам вопрос.

**Бонусы (продвинутый уровень)**

| Бонус | Реализация |
|---|---|
| Автоопределение типа | ключевые фразы и «покрытие полей» из конфига типа (`dekanat/classify.py`) |
| Плохие снимки | поиск листа и перспектива, выпрямление наклона, нормализация освещения, перебор вариантов, поворот 90/180°, повышение разрешения (`dekanat/ocr/`) |
| Новый тип без кода | описание полей в YAML-файле `config/doc_types/<тип>.yaml`; проверка — `python -m dekanat validate-config`; код не меняется |
| Подсветка на снимке | рамки каждого поля на исходном фото; клик по строке карточки → фрагмент на снимке |

## Что добавлено поверх базового сценария

Основной сценарий (документ → OCR → поля → Положение → вердикт со ссылкой на источник) **не менялся**; новые возможности лежат в отдельных модулях и маршрутах.

| Возможность | Где |
|---|---|
| Переключатель `USE_LOCAL_LLM`, единый `LLMService`, CPU-инференс Qwen2.5-3B-Instruct через Ollama, строгие промпты, проверка ответов модели | `dekanat/llm/` |
| Структурированный ответ: вывод, факты документа, пункты Положения, отсутствующее/сомнительное, оговорка о решении деканата | поле `answer.report` |
| Диалог-ассистент: конечный автомат и анкета перевода/зачисления | `dekanat/dialog/`, главная страница «Стол декана» |
| DOCX-шаблоны и автозаполнение | `dekanat/templates/` |
| Аккаунт администратора, шаблоны, документы базы знаний, обращения, статистика, история изменений | `dekanat/admin/`, `dekanat/storage/`, страница `/admin` |
| Сессии без регистрации, срок хранения и удаление данных | `dekanat/web/assistant.py`, раздел `privacy` в настройках |
| Несколько документов в базе знаний с версиями и переиндексацией | `dekanat/kb/manager.py` |
| Telegram-бот и Mini App, необязательные аккаунты (вход через Telegram), общие данные сайта и бота, уведомления об ответах деканата — **выключено по умолчанию** | `dekanat/telegram/`, `dekanat/accounts.py`, `dekanat/web/account.py` |

## Гибридный режим: правила по умолчанию, локальная модель по переключателю

Параметр `USE_LOCAL_LLM = False` задан в конфигурации буквально: значение по умолчанию — константа `USE_LOCAL_LLM = False` в [`dekanat/config.py`](dekanat/config.py), рабочее значение — ключ `USE_LOCAL_LLM: false` в начале [`config/settings.yaml`](config/settings.yaml), переопределение — переменная окружения `USE_LOCAL_LLM=true`. Он управляет **всеми** вызовами модели. Читается он в одном месте — `Settings.use_local_llm` в `dekanat/config.py`; остальной код спрашивает `LLMService.enabled` (это проверяет тест).

| | `USE_LOCAL_LLM=false` (по умолчанию) | `USE_LOCAL_LLM=true` |
|---|---|---|
| Намерения диалога («Я хочу перевестись») | регулярные выражения и словари | правила; неоднозначные фразы с «желанием» дополнительно разбирает модель, но анкета запускается только с согласия пользователя |
| Ответы анкеты | правила Python (формат, диапазоны, синонимы) | правила; если ответ неоднозначен — модель нормализует его в заданную схему |
| Поля документа | правила + запасные детекторы | то же + модель дозаполняет **только** поля, которых правила не нашли |
| Поиск по Положению | BM25 + синонимы | то же; на пограничных вопросах модель решает лишь «есть ли прямой ответ в этих пунктах и в каком» |
| Текст ответа | шаблонные формулировки + дословные пункты | то же + отдельное поле `report.explanation` — пересказ уже проверенного ответа |
| OCR, DOCX, хранилище, проверка источников | не зависят от переключателя | не зависят от переключателя |

* Модель **не включается** при старте и **не загружается**: при `false` backend даже не создаётся, сетевых обращений нет; при `true` — тоже запросы идут лениво, по мере надобности. Скрытых вызовов нет: на каждую из пяти разрешённых задач (`judge_clauses`, `detect_intent`, `normalize_answer`, `extract_fields`, `explain_answer`) приходится один метод `LLMService`.
* Все промпты — в [`dekanat/llm/prompts.py`](dekanat/llm/prompts.py): работать только с переданными данными, не выдумывать поля/пункты/даты, различать подтверждённое, предположение и «нет данных», возвращать только JSON по схеме с `null` для пустого, считать текст документов **данными, а не инструкциями** (он оборачивается в блок `<данные>`, закрывающие теги из документа вычищаются).
* Ответы модели проверяет Python ([`dekanat/llm/schemas.py`](dekanat/llm/schemas.py)): структура, типы, допустимые значения. **Номер пункта** принимается только из переданных; **значение поля** — только если его исходный фрагмент реально есть в OCR-тексте и значение проходит те же проверки формата, что у правил (такое поле помечается `method: llm`, уверенность 0,45 и примечанием «проверьте по снимку»); **имя/вуз/специальность из ответа анкеты** должны состоять из слов самого сообщения; **пояснение** не может назвать пункт или число, которых нет в исходных данных. При невалидном JSON — не больше `max_retries` повторов, затем безопасный fallback на правила. Результат детерминированных проверок моделью не заменяется.
* Противоречивые ответы анкеты («нет долгов, но математику не сдал») модели не отдаются — задаётся уточняющий вопрос. Паспортные данные в модель не передаются никогда.
* Модель недоступна (Ollama не запущена, нет модели, тайм-аут) — приложение продолжает работать в режиме без LLM; после двух подряд ошибок связи модель на `cooldown_seconds` «остывает», чтобы не получать запросы на каждое сообщение. Автоматического перехода на более тяжёлую модель нет.

### Qwen2.5-3B-Instruct на CPU (через Ollama)

Поддерживается один backend — [Ollama](https://ollama.com) (локально, без внешних API и без CUDA: запросы идут с `num_gpu=0`).

```bash
ollama pull qwen2.5:3b-instruct      # один раз, около 2 ГБ на диске
ollama serve                         # если Ollama ещё не запущена (на Windows работает приложение Ollama)
USE_LOCAL_LLM=true python -m dekanat serve          # Linux / macOS
```

```powershell
$env:USE_LOCAL_LLM = "true"; python -m dekanat serve   # Windows PowerShell
```

`python -m dekanat doctor` покажет, включена ли модель и доступна ли она. Параметры — в разделе `llm:` файла `config/settings.yaml`: `model`, `ollama_url`, `timeout`, `threads` (0 — решает Ollama), `num_ctx` (контекст), `max_input_chars` и `max_output_tokens` (ограничения длины), `max_retries`, `keep_alive` (сколько держать модель в памяти), `cpu_only`.

**Память.** Модель в 4-битной квантизации занимает порядка 2 ГБ на диске; с контекстом 4096 ей нужно, по оценке, 3–4 ГБ свободной оперативной памяти сверх самого сервиса и Tesseract. Это оценка, а не измерение. **Скорость не обещаем:** Qwen2.5-3B на этом проекте не измерялась. Для справки, на ноутбуке разработки (Intel Core 7 150U, 16 ГБ, без GPU) пять запросов к `llama3.1:8b` в необязательном интеграционном тесте заняли около 130 с.

Необязательный тест с настоящей моделью (по умолчанию пропускается):

```bash
DEKANAT_TEST_REAL_LLM=1 python -m pytest tests/test_llm_integration.py -s
```

## Диалог-ассистент и анкета

Ассистент встроен в главную страницу **«Стол декана»** — отдельной вкладки нет (старый адрес `/assistant` перенаправляет на `/`). Работает без регистрации, в браузерной сессии: в одной ленте можно задавать вопросы, проверять документ, исправлять распознанные поля, пройти анкету, получить DOCX и, по желанию, отправить обращение.

* **Куда идёт сообщение.** Новый файл — сразу проверка документа. Текст сначала разбирает анкета (`POST /api/assistant/message` с `defer: true`): «Я хочу перевестись», ответы на её вопросы, «верно», «исправить 3». Всё, что не относится к анкете, сервер не отвечает сам (`reply.kind = "passthrough"`) — стол запускает обычную проверку `/api/jobs` с этапами и подсветкой на снимке. Уточняющие вопросы к готовому ответу идут сразу в проверку.
* **Реплики анкеты** показываются в той же ленте: вопрос с отметкой «Вопрос N из M», лист сверки, быстрые ответы, выбор шаблона и кнопка «Сформировать документ», карточка готового DOCX и необязательная передача обращения с предпросмотром и подтверждением. Пока идёт анкета, поле ввода подсказывает «Ваш ответ на вопрос анкеты». Незавершённую анкету после перезагрузки страницы можно продолжить.
* **Документ сессии.** Проверка файла на столе сохраняет в сессии только карточку полей (без снимка и OCR-текста): из неё анкета берёт подсказки, а поля последней проверки можно исправить прямо в карточке (карандаш у поля, `PATCH /api/assistant/document/fields`; ответ пересчитывается на тот же вопрос). Если тот же файл проверяют снова, исправления пользователя сохраняются и ответ строится по ним; другой файл заменяет документ сессии. Без cookie сессии проверка работает как прежде и ничего не сохраняет.
* **Удалить мои данные** — пункт меню в верхней панели и команда в `Ctrl+K` (с подтверждением); отдельной строки про хранение данных под лентой нет.

Конечный автомат ([`dekanat/dialog/`](dekanat/dialog/)): `idle` → `screening` → `review` → `document_generation` → `completed`.

* **Намерения:** «Я хочу перевестись», «Как к вам поступить?», «Хочу перевестись в ваш вуз», «Мне нужно оформить заявление». Вопросы о правилах («В какой срок принимается решение о переводе?») и о документе («Хватит ли справки для перевода?») анкету **не** запускают. При намерении ассистент **предлагает** анкету; запускается она только после «да».
* **Чек-лист (фиксированный порядок):** 1) ФИО, 2) текущий вуз, 3) текущий курс, 4) специальность/направление, 5) форма обучения, 6) академические задолженности; затем — направление обращения (если не ясно из намерения), необязательные целевое направление и паспортные данные. Данные текущего вуза и целевые не смешиваются (`current_*` и `target_specialty`).
* **Для каждого вопроса:** проверка заполненности и формата, команды «назад», «исправить [поле]», «пропустить» (только необязательные), «заново», «отмена», «продолжить»; состояние сохраняется в БД после каждого ответа, к следующему вопросу ассистент переходит только после принятого ответа. Повторное «Я хочу перевестись» посреди анкеты её не перезапускает — только явное «заново».
* **«Нет» не универсально:** «нет» — ответ про задолженности, но ошибка на месте ФИО, вуза или курса. Оговорки («вроде», «наверное», «не помню») и противоречия дают уточняющий вопрос. Пример: «Да не, долгов вроде нет, всё закрыл» без модели уточняется; с моделью принимается только если она ответила однозначно.
* **Подсказки из документа:** если в сессии есть загруженная справка, ассистент предлагает значения из неё («В загруженном документе найдено…»; ответ «да» принимает). Вуз из справки — это *текущий* вуз.
* **Обзор:** собранные данные показываются списком (вместе с замеченными противоречиями с документом); документ создаётся **только после** явного «верно».

## DOCX-шаблоны и автозаполнение

Шаблон — обычный `.docx` с оформлением, шапкой и подписями, в тексте которого записаны переменные `{{ student_name }}`, `{{ passport_data }}`, `{{ current_university }}`, `{{ current_course }}`, `{{ current_specialty }}`, `{{ target_specialty }}`, `{{ education_form }}`, `{{ debts }}`, `{{ application_date }}`; можно добавлять и свои метки, в том числе по-русски (`{{ номер_зачётки }}`): данных от студента для них нет, поэтому в готовом заявлении останется «________», а в ответе секретаря метка называется читаемо («номер зачётки»). Учебные образцы — [`examples/templates/zayavlenie_o_perevode.docx`](examples/templates/zayavlenie_o_perevode.docx) (перевод) и [`examples/templates/zayavlenie_o_zachislenii.docx`](examples/templates/zayavlenie_o_zachislenii.docx) (зачисление) — не официальные формы.

```bash
python -m dekanat template-add examples/templates/zayavlenie_o_perevode.docx --name "Заявление о переводе"
python -m dekanat template-add examples/templates/zayavlenie_o_zachislenii.docx --name "Заявление о зачислении"
python -m dekanat template-sample my_template.docx                      # записать образец о переводе заново
python -m dekanat template-sample --kind enrollment my_template.docx    # образец о зачислении
```

То же — в кабинете сотрудника («Шаблоны»): новый шаблон или замена существующего (создаётся следующая версия; уже выданные студентам документы остаются доступными), скачивание, история версий, удаление. Нажатие на название данных копирует метку для вставки в Word. Если студент выбирает шаблон, который только что удалили, он получает понятное сообщение, а собранная анкета не теряется. В коде: `convert_to_template(file_path, ...)` и `fill_docx(template_path, data, output_dir)` в [`dekanat/templates/`](dekanat/templates/).

* `convert_to_template` проверяет, что файл существует, это `.docx`, он читается и безопасен (макросы, ActiveX, внешние шаблоны по ссылке и «архивные бомбы» отклоняются), сохраняет его во внутренний каталог `/templates/` проекта (`templates/<id>/vN.docx`; путь задаёт `storage.templates_dir`) и возвращает идентификатор и список найденных плейсхолдеров. **Чужой шаблон не затирается:** для замены нужны явные `template_id=...` и `overwrite=True`, прежняя версия остаётся в истории.
* Заполнение работает с основным текстом, таблицами (в том числе вложенными), надписями и колонтитулами; плейсхолдер, который Word разбил на несколько runs, склеивается, форматирование первого run сохраняется. Исходный шаблон не меняется, готовый файл получает уникальное имя в `storage.output_dir`.
* **Недостающие данные не выдумываются:** в документе студента на месте такой метки ставится строка «________» для заполнения от руки (`fill_docx(..., blank_unfilled=True)`; без этого флага метка остаётся как есть), а имя поля попадает в список `unfilled` — ответ ассистента перечисляет такие поля. Ключи данных, которых нет в шаблоне, возвращаются в `unused`.
* Документ не отправляется в деканат автоматически: его скачивает сам пользователь. Отправка обращения — отдельный шаг с подтверждением (ниже).

## Аккаунты, роли и страница администратора

Страница **`/admin`** («Кабинет сотрудника»; вход — кнопка «Сотрудникам»). Переключатель **«Стол декана | Сотрудникам»** есть на обеих страницах (на столе он появляется, когда сотрудник вошёл), поэтому повторно входить при переходе туда и обратно не нужно: вход действует `admin.session_hours` часов.

Разделы кабинета (закладки со счётчиками, адрес закладки запоминается — `/admin#tickets`):

* **Обзор** — период 7 / 30 / 90 дней: посещения, вопросы и проверки, начатые анкеты, сформированные документы (у каждого показателя — линия за период и сравнение с прошлым периодом), передано в деканат; столбцы «Обращения по дням» с подсказкой и переключателем «График | Таблица»; популярные темы с долями; чем заканчивались ответы; путь анкеты (начали → получили документ → передали в деканат); сводка.
* **Обращения** — спокойное рабочее место на одной «бумаге»: **список слева, карточка справа**, у каждой части свой скролл. Интерфейс намеренно не нагружен: цвет есть только у точки статуса (красная — новое, жёлтая — в работе, зелёная — обработано, серо-синяя — отклонено), а всё второстепенное появляется по требованию. **Список:** заголовок со сводкой («15 обращений · 7 новых»), поиск по имени, номеру и теме (ё = е), кнопка фильтров (даты, тип, тема — в окошке под ней, там же «Сбросить» и «Выгрузить CSV»), статусы — тихие вкладки с подчёркиванием (число — у «Новые» и «В работе»); строка — точка статуса, имя, суть и номер, время. При наведении точка превращается в флажок, а время — в кнопку «Обработано» (один щелчок, в сообщении есть «Отменить»). Переход по списку стрелками ↑ ↓. **Выбор нескольких обращений:** «Выбрать» (или флажок у строки) → тёмная панель «В работе / Обработано / Отклонено / Ответ» с необязательным общим ответом студентам (`POST /api/admin/tickets/bulk`, до 200 номеров за раз; «Отклонено», общий ответ и выбор больше пяти спрашивают подтверждение; после смены статуса есть «Отменить»). В истории каждого обращения остаётся запись «статус: … (вместе с другими обращениями)»; выбор действует только на показанные в списке обращения. **Карточка:** крупное имя, суть и время, переход к соседним обращениям («3 / 15»), статус одним щелчком (с «Отменить»), заявка, ответ студенту с заготовками, заметка (за ссылкой «Добавить заметку», пока её нет) и лента истории (три последних, остальное — «Показать ещё»). На телефоне список и карточка идут друг под другом.
* **Шаблоны** — список с главным действием «Скачать» и меню «⋯» (заменить файл, история версий, удалить); добавление по выбору файла (перетащить или нажать), кнопка активна, когда файл выбран; названия данных подставляются понятными словами, нажатие копирует метку для вставки в документ Word.
* **База знаний** — переключатель «В ответах» вместо кнопок «Отключить / Включить», меню «⋯», «Обновить поиск».
* **История** — лента по дням с понятными подписями, фильтр «Всё / Шаблоны / База знаний / Обращения / Входы».
* **Аккаунт** — смена пароля.

Удаления подтверждаются диалогом в самой странице (Esc и клик мимо — отмена), без технических идентификаторов и контрольных сумм. Страница без сборки (HTML, CSS, JavaScript; строгий CSP), в тёмной и светлой темах, на телефоне раскладка в одну колонку.

Все административные операции (`/api/admin/*`, а также правка Положения и типов документов) проверяют права **на сервере**; скрытие кнопок защитой не является.

* **Универсального пароля нет.** Первого администратора создаёт ответственный за сервер:

  ```bash
  python -m dekanat create-admin --username dean          # пароль вводится скрыто, дважды
  python -m dekanat create-admin --username dean --password-env MY_ADMIN_PASSWORD   # из переменной окружения; в аргументах пароль не принимается
  ```

  Пароль забыт? В базе только хэш, восстановить его нельзя, но ответственный за сервер может задать новый (все входы этой записи завершатся):

  ```bash
  python -m dekanat reset-admin-password --username dean
  ```

  Для контейнера есть запасной путь: `DEKANAT_ADMIN_USERNAME` + `DEKANAT_ADMIN_PASSWORD` в окружении при первом запуске (если админов ещё нет); потом уберите пароль из окружения. Секреты в репозитории не хранятся.
* Пароли хранятся только как хэш scrypt с солью; политика: не короче `admin.min_password_length` (10), без простых и совпадающих с логином. Неверный пароль просто отклоняется, без ожидания; блокировка входа после серии неудачных попыток необязательна и по умолчанию выключена (`admin.max_login_failures` и `admin.lockout_minutes` > 0 включают её — для сервиса в интернете так лучше). Неудачные входы пишутся в историю. Подбор замедляют scrypt и политика паролей. Сессия — случайный токен в `HttpOnly`-cookie `SameSite=Strict`; на сервере хранится только его хэш. Изменяющие запросы с чужим `Origin` отклоняются.
* Администратор может: добавлять, смотреть, заменять (с версиями), скачивать и удалять шаблоны; загружать, заменять, отключать и удалять документы базы знаний и основное Положение, запускать переиндексацию; смотреть обращения по переводу и зачислению, фильтровать их по дате, типу, статусу и теме и менять статус; смотреть статистику; смотреть журнал изменений (кто, когда, что: шаблоны, документы, типы документов, учётные записи — без паролей и содержимого).
* **Проверка ответов базы знаний.** В «Базе знаний» кнопка «Проверить ответы» задаёт секретарю контрольные вопросы из `config/golden_questions.yaml` (ожидаемый пункт или честное «нет ответа») и показывает, что сошлось, а что нет: так видно, не сломались ли ответы после замены Положения или добавления документа. Вопросы в репозитории написаны для учебного Положения; заменили Положение — замените и вопросы.
* **Заготовки ответа студенту.** Над полем «Ответ студенту» — кнопки с готовыми формулировками (вставляются и правятся до сохранения). Свои — в `config/reply_templates.yaml` (`templates: [{title, text}]`); без файла или при ошибке в нём работают стандартные.
* **Возможные дубли.** В карточке обращения сотрудник видит, если студент с тем же ФИО (регистр, «ё» и лишние пробелы не важны) уже обращался раньше: номера и статусы прошлых обращений.
* Редактирование Положения (кнопка «Заменить Положение» на вкладке «Положение» видна только вошедшему сотруднику; то же делается в кабинете: «База знаний» → «Основное Положение») и типов документов через REST (`PUT /api/doctypes/{id}`) требует входа администратора (`admin.protect_edit: true`). Для чисто локального запуска без учётных записей можно поставить `admin.protect_edit: false` — тогда всё работает как раньше, но **не открывайте такой сервис в интернет**. `server.allow_edit: false` по-прежнему полностью запрещает правки.
* Пользователь без аккаунта к `/api/admin/*` доступа не получает, даже если у него есть живая пользовательская сессия.

### Документы базы знаний

Администратор загружает регламенты (`.txt`, `.md`, `.docx`, `.pdf` с текстовым слоем). Нумерация пунктов («3.4.», «п. 3.4») определяется автоматически, структура разделов сохраняется. Основное Положение сохраняет свою нумерацию («п. 3.4 Положения»); пункты дополнительных документов получают ключ `<id документа>:<номер>` и подпись «п. 3.4 (Название документа)». После добавления, замены, отключения и удаления индекс пересобирается сразу: удалённые и устаревшие пункты в ответах не появляются. Каждая версия текста хранится в истории. Замена основного Положения из файла возможна и из интерфейса «Положение»; пункт меню «Вернуть Положение из файла» убирает замену.

Как это выглядит для сотрудника и для студента (проверено на живом сервере и тестами `tests/test_knowledge_base_flow.py`):

* Сотрудник в кабинете: «База знаний» → выбрать файл (перетащить или нажать) → «Добавить документ». Секретарь сразу отвечает и по нему, со ссылкой вида «п. 2.1 документа «Правила общежития»». Переключатель «В ответах» выключает документ, «⋯» → «Заменить файл…» создаёт новую версию (старый текст сразу перестаёт отвечать), «История версий» показывает все версии.
* Если в файле нет нумерации пунктов, он всё равно принимается: абзацы нумеруются подряд («§1», «§2»), а сотрудник видит предупреждение, что ссылки будут такого вида и как их сделать точными. Пустой, повреждённый, слишком большой файл и файл не того формата отклоняются понятным сообщением; название документа должно быть уникальным.
* Студент: без документа на столе вопрос идёт к Положению и всем включённым документам («Сколько стоит проживание в общежитии?» → п. 2.1 загруженных правил). Если на столе лежит документ, секретарь отвечает по нему, а по Положению — когда оно названо или по подсказке «— по Положению?».
* Совпадение только через синонимы (например, «стоит» ~ «плата») без общих слов с вопросом ответом не считается: «Сколько стоит обучение?» остаётся «нет информации», даже если в базе есть плата за общежитие.

## Хранение, приватность и статистика

* **Что хранится и где.** SQLite `storage.db_path` (по умолчанию `data/storage/dekanat.db`): сессии пользователей и их анкеты, карточка полей загруженного документа, метаданные готовых документов, обращения, события статистики, учётные записи и журнал изменений. Файлы: шаблоны (`templates/`) и готовые документы (`data/output/`). Содержимое `data/storage`, `data/output` и `templates/` не входит в репозиторий (`.gitignore`).
* **Минимизация.** Загруженный снимок и OCR-текст на диск и в БД **не сохраняются** — после проверки в сессии остаются только значения полей карточки. Единственное исключение — кеш в памяти процесса: результаты OCR последних `ocr.cache_size` (по умолчанию 4) файлов хранятся, чтобы повторные вопросы по тому же файлу не запускали распознавание заново; при перезапуске он пропадает, `ocr.cache_size: 0` его отключает. Паспортные данные необязательны, в модель не попадают, в обращение не включаются, пока пользователь сам не отметит это.
* **Сроки.** `privacy.session_ttl_hours` (24) — сессия без активности удаляется вместе с анкетой и данными документа; `generated_ttl_hours` (24) — готовые документы; `passport_ttl_minutes` (60) — паспортные данные удаляются из анкеты через час после ввода (в документе поле тогда остаётся незаполненным и сообщается как «нет данных»); `ticket_retention_days` (180) — обращения; `event_retention_days` (365) — события статистики. Чистка выполняется при старте и при обращениях к ассистенту (не чаще раза в 10 минут; отдельных фоновых процессов нет); вручную — `python -m dekanat purge` или кнопка в панели. Пользователь в любой момент может нажать «Удалить мои данные» (`DELETE /api/assistant/data`).
* **Изоляция сессий.** Идентификатор сессии — случайный токен в `HttpOnly`-cookie; все данные привязаны к нему на сервере. Чужой документ или анкету получить нельзя даже по известному идентификатору документа (загрузка проверяет владельца сессии). Истёкшая сессия — понятное сообщение, данные удалены.
* **Аккаунты (необязательные).** Вход через Telegram продлевает срок жизни данных (`accounts.*`, см. раздел про Telegram); без входа действуют сроки выше. Аккаунт и его данные удаляются по просьбе человека сразу.
* **Статистика** хранит только дату и время, хэш сессии (не сам cookie), категорию вопроса, тип сценария, статус обработки и факты «анкета запущена / документ сформирован / обращение отправлено или отклонено». Текст вопросов, OCR, ФИО и паспортные данные в события и обычные логи не попадают; IP-адреса и геолокация не определяются и не сохраняются.
* **Отправка в деканат.** Единственный поддерживаемый канал — внутренняя очередь обращений (`delivery.channel: queue`), которую читают администраторы в `/admin`. Канал считается доступным, только если в системе есть хотя бы один администратор. Перед отправкой пользователю показывается состав передаваемых данных и запрашивается подтверждение; к обращению прикладывается готовый документ; повторная отправка той же анкеты возвращает уже созданное обращение; отказ ничего не отправляет. Если канал не настроен (`delivery.channel: none`) или нет администратора, сервис честно пишет, что автоматическая отправка пока недоступна, и предлагает скачать документ. Отправка по e-mail не реализована.
* **Когда обращение не отправляется.** В очередь деканата уходит только анкета, у которой все обязательные ответы заполнены и проходят проверку формата, указано целевое направление и **нет академических задолженностей** (`dekanat/dialog/eligibility.py`). Иначе сервер отвечает отказом с причиной (409), а интерфейс не показывает кнопку «Передать в деканат» и объясняет, почему; о запрете студент узнаёт ещё на сверке анкеты, пока ответы можно исправить. Готовый документ скачать можно всегда. Правила вуза вынесены в `config/settings.yaml`: `submission.allow_debts` (по умолчанию `false`) и `submission.require_target_specialty` (по умолчанию `true`). Учебное Положение других проверяемых по анкете условий не содержит: наличие мест (п. 7.1), справка об обучении (п. 7.2) и решение (п. 7.3) остаются за сотрудником деканата.
* **«Что дальше» после готового заявления.** Под готовым документом секретарь пишет, что понадобится принести и к какому сроку ждать решения. Это ответы на те же вопросы, что студент мог бы задать сам («Какие документы нужны для перевода?», «В течение скольки дней принимается решение?»), поэтому они берутся из действующего Положения со ссылкой на пункт (`dekanat/dialog/nextsteps.py`) и меняются вместе с ним. Срок считается в рабочих днях (суббота и воскресенье не в счёт, праздники не учитываются) и подаётся как ориентировочный. Если в Положении об этом ничего нет (в учебном — про зачисление), блок не показывается.
* **Статус обращения без входа.** При отправке студент получает номер и код (например, `K7M2-QX9P`; в базе хранится только хэш кода вместе с номером). На странице «Статус обращения» (меню или `Ctrl+K`) по номеру и коду видны статус и **ответ деканата**, который сотрудник пишет в кабинете в поле «Ответ студенту»; заметки сотрудника и данные анкеты наружу не уходят. На неверный номер и неверный код один и тот же ответ, с одного адреса разрешено не больше 8 неверных попыток за 10 минут (429). При отправке можно по желанию указать контакт (почта, телефон или `@telegram`): он виден студенту в составе передаваемых данных до отправки и сотруднику в обращении. Сотрудник может выгрузить обращения с текущими фильтрами в CSV («Выгрузить CSV» над списком; ячейки-формулы обезврежены, файл открывается в Excel).
* **Письмо с номером и кодом (по желанию).** Код всегда показывается студенту на экране: секретарь пишет его в чате, называет, что стало с письмом, и предлагает открыть страницу статуса. Если студент указал **почту** и сервер настроен на отправку писем (`mail.*` в `config/settings.yaml`: `enabled`, `host`, `port`, `security`, `username`, `from`, `public_url`; пароль — только в переменной окружения `DEKANAT_MAIL_PASSWORD`), на неё уходит письмо с номером, кодом и ссылкой (без ФИО и данных анкеты; адрес в ответах сервера маскируется: `i***@example.com`). По умолчанию отправка выключена — тогда сервис прямо говорит, что письмо не отправляется, а код остаётся на экране. Сбой почтового сервера не мешает обращению. Телефон и Telegram в контакте письмо не вызывают.

## Telegram-бот, Mini App и необязательные аккаунты

> **Всё выключено по умолчанию** (`telegram.enabled: false`). Без токена бота сайт работает как раньше: анонимная сессия в браузере, без регистрации — как требует ТЗ. Аккаунт никому не нужен, чтобы проверить документ, задать вопрос или пройти анкету.

**Что умеет бот** (личный чат, по-русски; меню под полем ввода, команды и кнопки дублируют друг друга):

| Что | Как это выглядит |
|---|---|
| Проверить документ | фото или PDF → «⏳ Читаю документ…» со шкалой этапов → карточка полей (составные поля одной строкой, как на сайте) и ответ со ссылкой на пункт Положения; кнопки быстрых вопросов («Чего не хватает?», «Хватит для перевода?»); на «покажи …», «найди …», «где …» бот сразу присылает текст ответа и снимок с подсветкой (и крупный план, если место маленькое) — без нажатия кнопки; кнопки «🖼 Показать на снимке» (фото с подсветкой найденного), «📝 Составить заявление», «⏰ Напомнить через 3 дня», «🗑 Забыть документ» |
| Вопрос по Положению | обычное сообщение; если ответа нет ни в документе, ни в Положении, бот так и говорит |
| Анкета → DOCX | `/form`: вопросы текстом и кнопками («Назад», «Отмена»), заявление приходит в чат файлом |
| Обращение в деканат | предпросмотр «что уйдёт в деканат», подтверждение, номер и код; `@имя` для связи добавляется только по явной кнопке, паспортные данные не отправляются |
| Мои обращения | `/tickets` без кода (если обращение отправлено из аккаунта); `/status номер код` — по коду, с кнопкой «Присылать ответы сюда» |
| Уведомления | ответ деканата и смена статуса приходят в чат; напоминания «что принести / к какому сроку»; `/settings` — выключить |
| Данные | `/forget` (анкета, документ, файлы), `/privacy` (что хранится), удаление аккаунта |
| Mini App | кнопка «🌐 Приложение»: тот же сайт внутри Telegram, вход выполняется сам |

Нажатие любой кнопки подтверждается сразу коротким «тостом» (например, «Отправляю в деканат…»), поэтому бот не выглядит зависшим.

**Включить** (токен выдаёт @BotFather; **только в переменной окружения**, в репозиторий и `settings.yaml` его писать нельзя):

```bash
export DEKANAT_TELEGRAM_ENABLED=true
export DEKANAT_TELEGRAM_BOT_TOKEN=123456:ABC...     # Windows PowerShell: $env:DEKANAT_TELEGRAM_BOT_TOKEN = "..."
python -m dekanat serve          # бот запускается вместе с сайтом (долгий опрос: публичный адрес и открытые порты не нужны)
python -m dekanat bot --setup    # один раз: команды, описание и кнопка меню бота
```

Другие режимы: `telegram.mode: webhook` (Telegram присылает сообщения на `telegram.public_url`, нужен https; адрес содержит секрет, запрос проверяется по секретному заголовку); `telegram.run_in_server: false` и `python -m dekanat bot` — бот отдельным процессом. Для кнопки Mini App нужен https-адрес сайта в `telegram.public_url` (обратный прокси с сертификатом); без него всё остальное работает, кнопки приложения просто нет. `telegram.staff_chat_id` — чат сотрудников, куда приходит «Новое обращение № …». `python -m dekanat doctor` показывает состояние бота. Остальные параметры — в блоках `telegram:` и `accounts:` файла `config/settings.yaml`. Аватар бота в стиле сайта — `docs/telegram/bot-avatar.png` (1024×1024; в @BotFather: `/setuserpic`); пересобрать — `python scripts/make_bot_avatar.py`. Приветственная картинка («Что умеет этот бот?») — `docs/telegram/bot-welcome.png` (640×360; `/setdescriptionpic`), пересобрать — `python scripts/make_bot_welcome.py`.

**Вход на сайте через Telegram (необязательный).** При заходе на сайт показывается спокойный баннер: «Войти через Telegram» (с тремя плюсами: начатое на телефоне заканчивается на компьютере, ответ деканата приходит в Telegram, свои обращения видны без кода) или «Напомнить позже» (через 3, затем 7, затем 30 дней; запоминается в браузере). Баннер не показывается вошедшим, внутри самого Telegram и если бот не включён; войти можно и из меню. Как проходит вход:

1. Сайт создаёт одноразовую ссылку `t.me/<бот>?start=login_…` (в базе хранится только хэш токена; живёт 5 минут; привязана к cookie именно этого браузера).
2. Человек открывает бота и **подтверждает вход кнопкой** (бот показывает, с какого устройства запрос: «Chrome, Windows · 203.0.*.*»). Само открытие ссылки ничего не даёт — так чужую ссылку нельзя «подсунуть» тихо; кнопка «Это не я» отклоняет запрос.
3. Сайт, опрашивая сервер, получает вход. Cookie сессии **заменяется новой** (старый идентификатор больше не работает); данные анонимной сессии переходят в аккаунт, если там своих ещё нет.

Внутри Telegram (Mini App) вход автоматический: Telegram передаёт подписанные данные пользователя, сервер проверяет подпись (HMAC-SHA256 от токена бота, срок `telegram.initdata_max_age_hours`), неверные и устаревшие данные отклоняются, неудачные попытки ограничены. Скрипт Telegram подгружается **только** внутри Mini App; обычные посетители ничего постороннего не загружают.

**Синхронизация сайта и бота.** У аккаунта одна «сессия данных»: анкета, карточка проверенного документа, готовые DOCX и обращения. Сайт (после входа) и бот работают с ней через одно и то же ядро (`AssistantCore`), поэтому анкету можно начать в боте, продолжить на сайте и наоборот; параллельные записи защищены блокировками. Выход с одного устройства данные не удаляет, «Удалить мои данные» стирает их и на сайте, и в боте.

**Что хранится.** Telegram-идентификатор, имя и @имя (телефон и почту не запрашиваем), анкета, карточка полей документа, готовые файлы, обращения, очередь уведомлений. Снимки и PDF **на диск и в базу не пишутся**: бот помнит идентификатор файла Telegram, чтобы повторить вопрос по тому же документу; в памяти процесса держатся до трёх последних файлов (пропадают при перезапуске и при «Забыть документ» / `/forget`), иначе файл скачивается заново. Сроки: вход на сайте — `accounts.session_days` (30) без активности, данные аккаунта — `accounts.data_days` (90), сам аккаунт без единого входа и сообщения — `accounts.retention_days` (365). Скачать всё, что хранится о человеке (`/api/account/export`), и удалить аккаунт можно в «Аккаунте» на сайте; удаление аккаунта не удаляет отправленные обращения (они остаются у деканата без привязки к человеку).

**Полезное сверх просьбы:** уведомление, когда сотрудник ответил или сменил статус (очередь в базе с повторами, защитой от дублей и ограничениями Telegram; тому, кто заблокировал бота, больше не пишем); «Мои обращения» без кода и привязка прежнего обращения по номеру и коду; напоминания «что принести»; фото с подсветкой найденного; сообщение сотрудникам о новом обращении; выгрузка и удаление своих данных; ограничения частоты (`telegram.rate_per_minute`, `telegram.files_per_hour`).

### Telegram и требования ТЗ

* ТЗ запрещает внешние **языковые модели** (GigaChat, YandexGPT и подобные) — они не используются: распознавание текста, поиск по Положению и ответы остаются на сервере деканата, как и раньше. Telegram — только канал доставки, а не источник ответов.
* ТЗ допускает интерфейс «веб-страница или Telegram-бот»: бот и Mini App — допустимый интерфейс, а сайт остаётся основным и самодостаточным.
* ТЗ требует работы **без регистрации** (браузерная сессия): аккаунт необязателен, баннер откладывается, всё работает без входа.
* **Честная оговорка.** Telegram — сторонний сервис: сообщения, фото и PDF, которые человек присылает боту, проходят через серверы Telegram, как в любой переписке. Если для организации это неприемлемо, бот просто не включают — сайт полностью работает без него. Токен бота хранится только в окружении.
* **Что не проверялось.** Бот, вход и Mini App проверены тестами и сквозным прогоном на **поддельном** Bot API (в среде разработки нет настоящего токена); с живым Telegram и реальным https-адресом они не запускались. Бот работает только в личных чатах; файлы ограничены лимитом Bot API (20 МБ); QR-кода для входа нет (ссылку можно скопировать и открыть на телефоне). Mini App рассчитан на приложения Telegram (телефон, компьютер); в веб-версии Telegram сайт открывается во встроенном окне, где браузер может не принимать cookie, — там лучше открыть сайт обычной ссылкой.

## Быстрый старт

### 1. Установите Tesseract с русским языком

* **Windows:** установщик [UB Mannheim](https://github.com/UB-Mannheim/tesseract/wiki) — при установке отметьте язык **Russian**. Сервис сам найдёт `C:\Program Files\Tesseract-OCR\tesseract.exe` (можно задать путь в `config/settings.yaml` → `ocr.tesseract_cmd` или переменной `TESSERACT_CMD`).

**Если сверху плашка «Проверка документов сейчас недоступна».** Это значит, что сервер не смог запустить Tesseract. Причину называет команда `python -m dekanat doctor`; сотрудник видит её же с готовыми шагами в кабинете («Кабинет сотрудника» → верх страницы). Частые случаи:

* **Tesseract поставили, пока сервер уже работал.** Перезапуск не нужен: сервис ищет Tesseract заново примерно раз в полминуты — обновите страницу. Если плашка осталась, перезапустите сервер.
* **Нет русского языка** (установщик по умолчанию ставит только английский). Выполните в папке проекта `python -m dekanat fetch-lang`: команда скачает `rus`, `eng` и `osd` в `data/tessdata` (права администратора не нужны, адрес — официальный репозиторий tessdata_fast), сервис подхватит папку сам. Либо запустите установщик ещё раз и отметьте Russian в разделе «Additional language data».
* **Tesseract поставлен в другую папку.** Сервис смотрит в `C:\Program Files\Tesseract-OCR`, в папку пользователя и в реестр Windows (туда установщик записывает свою папку); если не нашёл — укажите путь к `tesseract.exe` в `config/settings.yaml` → `ocr.tesseract_cmd` или в переменной `TESSERACT_CMD`.
* **В окружении осталась неверная `TESSDATA_PREFIX`** (от старых инструкций). Сервис сам пробует без неё и с папкой `tessdata` рядом с `tesseract.exe` и запоминает рабочий вариант; переменную всё равно лучше удалить.
* **Сервис запущен в Docker.** В образе свой Tesseract с русским; Tesseract, установленный в Windows, контейнеру не виден и ему не нужен.

* **Linux:** `sudo apt install tesseract-ocr tesseract-ocr-rus tesseract-ocr-osd`
* **macOS:** `brew install tesseract tesseract-lang`

### 2. Поставьте зависимости

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m dekanat doctor        # проверка окружения
```

Нужен Python 3.10 или новее (проверено на 3.14).

### 3. Запустите

```bash
python -m dekanat serve         # → http://127.0.0.1:8000   (модель выключена: USE_LOCAL_LLM=false по умолчанию)
python -m dekanat create-admin --username dean      # по желанию: учётная запись для /admin и правки Положения
```

**Windows, одной командой.** `start.ps1` (или двойной щелчок по `start.bat`) запускает сайт, а если рядом лежит файл `.telegram-token` с токеном бота (одна строка, файл в `.gitignore`), то и Telegram-бота — одним процессом:

```powershell
.\start.ps1              # сайт http://127.0.0.1:8000 и, если есть токен, бот
.\start.ps1 -Port 8001   # другой порт
.\start.ps1 -DryRun      # только показать, что будет запущено
.\start.ps1 -Restart     # порт занят прежним запуском — остановить его и запустить заново
```

Остановка — Ctrl+C. Два запуска на одном токене одновременно невозможны: Telegram отдаёт одному опросу бота, второй получает ошибку конфликта.

Откройте страницу, кликните по примеру на столе (или перетащите своё фото) и задайте вопрос; анкета запускается там же — напишите «Я хочу перевестись». Панель сотрудников — `/admin` (пункт «Вход для сотрудников» в меню верхней панели). Включение локальной модели — в разделе «Гибридный режим».

Готовый интерфейс (React) уже собран и лежит в `dekanat/web/static/app/` — **Node.js для запуска не нужен**. Он нужен только тем, кто хочет править интерфейс (см. «Интерфейс на React»).

### Docker (по желанию)

```bash
docker build -t online-dekanat .
docker run -p 8000:8000 -v dekanat-data:/app/data/storage -v dekanat-out:/app/data/output -v dekanat-tpl:/app/templates \
  -e DEKANAT_ADMIN_USERNAME=dean -e DEKANAT_ADMIN_PASSWORD='ваш-пароль-не-короче-10-символов' online-dekanat
```

Тома нужны, чтобы база, шаблоны и готовые документы переживали пересоздание контейнера; пароль администратора из окружения используется только при первом запуске, потом уберите его. Локальная модель из контейнера доступна по `llm.ollama_url` (например, `DEKANAT_LLM_OLLAMA_URL=http://host.docker.internal:11434` и `USE_LOCAL_LLM=true`).

`Dockerfile` написан по описанию и в среде разработки **не собирался** — Tesseract в нём ставится из `apt`. В контейнере редактирование типов документов и Положения из интерфейса выключено (`DEKANAT_SERVER_ALLOW_EDIT=false`).

## Как пользоваться

### Веб-интерфейс: «Стол декана»

Слева — **диалог** с цифровым секретарём, справа — **стол с документом**. Всё, что требует ТЗ, на виду:

| Требование ТЗ | Где в интерфейсе |
|---|---|
| Принять документ (JPG/PNG/PDF) и вопрос на русском | перетащить файл на стол, «Выбрать файл», скрепка в панели ввода, вставка из буфера (`Ctrl+V`), камера на телефоне; поле вопроса внизу |
| Тип документа можно выбрать вручную | кнопка типа в панели ввода («Определить автоматически» / один из типов / «Другой документ») и рейка «Тип документа» в ответе — в один клик пересчитывает как другой тип |
| Карточка полей, «не найдено» | блок «Карточка документа»: все поля типа, что не найдено — так и написано; уверенность распознавания у каждого значения |
| Три вида ответов с формулировками из ТЗ | «Заключение» со штампом: «В порядке» / «Не хватает» / «Ответа нет» и текст ответа |
| Источник: пункт Положения или поле документа | чипы «Источник»: клик по «п. 3.4» открывает боковую панель с текстом пункта и соседними пунктами; клик по полю — приближает снимок |
| Бонус: подсветка на снимке | рамки на листе и **вырезка фрагмента фото** прямо в ответе; наведение на строку карточки подсвечивает поле, камера плавно подлетает к нему |
| Бонус: автоопределение типа | рейка типа показывает, как определён тип и с какой уверенностью; для чужих документов — «не похож ни на один из известных» |
| Бонус: новый тип без кода | файл `config/doc_types/<тип>.yaml` с полями и ключевыми фразами; `python -m dekanat validate-config`; тест `tests/test_new_doctype.py` |

Сцена пустого стола — лоток для документа и «примеры на столе» (клик по примеру сразу запускает проверку). Пока идёт проверка, **реальные этапы** (файл → чтение текста → тип → карточка → ответ), луч сканера над листом, время и кнопка остановки (`Esc`). Ответ приходит «штампом»; предыдущие ответы сворачиваются в строки, диалог можно продолжать вопросами по тому же документу.

Приёмы интерфейса: масштаб колесом и щипком, перетаскивание, миникарта при увеличении, двойной щелчок — приблизить; `Ctrl+K` — палитра команд (переходы, примеры, поиск по пунктам Положения); `Enter` — отправить, `Shift+Enter` — новая строка; `/` — к полю вопроса; `?` — подсказка по клавишам. Тема: светлая («дневной стол»), тёмная («ночная лампа») или как в системе. История вопросов хранится только в браузере, без снимков. Заключение можно распечатать (`Ctrl+P`: в печать идёт только заключение и карточка); выгрузка в JSON — в командной строке (`ask --json`, `batch`).

**Откуда берётся ответ.** Пока на столе лежит документ, секретарь отвечает **по документу**: «покажи ФИО», «покажи название вуза», «где печать», «кто студент» находят поле, **выделяют его на снимке и приближают**; «хватит ли справки?» — проверка комплектности по требованиям Положения. Если ответа в документе нет, а в Положении он есть, секретарь так и говорит и предлагает тот же вопрос «— по Положению?» (одним щелчком). По Положению он отвечает, когда оно **названо** в вопросе («по Положению», «согласно регламенту», «что сказано в пункте 3.4») и когда документа на столе нет. Режим включён для стола и чата; пакетный режим и CLI (`batch`, `ask`) работают как в кейсе — по полям документа и пунктам Положения.

Дополнительные удобства:
* **Другой документ.** Над снимком — кнопка «Другой документ» и лента документов на столе: можно положить второй файл, проверить его и вернуться к первому, не теряя ответов. Для только что положенного файла появляется кнопка «Проверить документ целиком».
* **Спросить дальше.** Под ответом — вопросы, которые сервис точно умеет разобрать (по найденным полям, правилам Положения, для чужого документа — по его тексту): один щелчок, и вопрос уходит по тому же документу.
* **Снимок под углом.** Подсветка идёт **вдоль строки**: если лист сфотографирован с наклоном, рамка поля — наклонный четырёхугольник, а не осевой прямоугольник, раздутый до размеров всей строки и съехавший с неё. Распознавание идёт по выпрямленному листу, и рамки переносятся обратно на исходный снимок вместе с наклоном (`OcrPage.map_box` отдаёт `quad` — четыре угла; у прямого снимка его нет). Так рисуются рамки на листе, вырезка фрагмента в ответе, «снимок с подсветкой» (PNG) и оверлей командной строки.
* **Текст документа.** Кнопка «Текст» под снимком открывает распознанный текст: поиск с подсветкой совпадений и счётчиком, «Копировать», «Скачать .txt»; «На снимке» отправляет найденную фразу вопросом «Где на документе «…»?».
* **Где на документе «фраза».** Вопросы «где на документе «предмет договора»?», «покажи, где слово итого», «найди «ИНН»» ищут саму фразу в распознанном тексте (точно, а также с запасом на опечатки OCR и другие формы слова) и подсвечивают **все** найденные места на снимке, в том числе вдоль строки на снимке под углом; нет такой фразы — «не нашлось», без выдумок. «Покажи значение «ИНН»», «какая сумма в строке «Итого»» по-прежнему отвечают значением, а не поиском слова. «Выведи весь текст документа», «распознай текст с картинки» отдают распознанный текст (начало — в ответе, целиком — в панели «Текст»); вопросы про часть текста («текст пункта 1.2», «последний абзац») работают как раньше.
* **Копировать ответ** (вердикт, текст и источник) и **сохранить снимок с подсветкой** (PNG с рамками найденных полей) — для переписки со студентом или отчёта.
* **Контраст.** Переключатель в панели снимка повышает контраст бледных и тёмных фото, чтобы глазами сверить результат OCR.
* **Изменить вопрос** (карандаш у реплики), `↑` в пустом поле возвращает прошлый вопрос.
* Мобильная раскладка: стол сверху, диалог под ним; панель ввода компактная.
* **Одна карточка на документ.** Карточка полей, выбор типа и правка значений показываются у первого ответа по файлу; уточняющие вопросы по тому же документу дают только ответ и ссылку «Показать» на карточку (если тип пересчитан — у нового ответа своя карточка).
* **Прекратить анкету** — кнопка в полосе «Идёт анкета» под шапкой диалога, пока анкета идёт (подтверждение на том же месте: «Ответы удалятся.» — «Прекратить» / «Нет»), и третья кнопка «прекратить» в карточке «Анкета не завершена». Ответы анкеты удаляются, чат возвращается к обычным вопросам; то же делают слова «отмена», «прекратить», «стоп», «хватит» в поле ввода.
* **Очистить чат** — кнопка в шапке диалога (и команда в `Ctrl+K`) равна «Удалить мои данные»: сервер забывает сессию (анкету, карточку документа, готовые файлы), реплики «сметаются» с ленты, и чат с секретарём начинается с нуля, с приветствия. Если сервер данные удалить не смог, на экране ничего не сбрасывается и показывается ошибка.
* **Положение (вкладка).** Пункты документов базы знаний показаны отдельными разделами «Документ «…»» с обычными номерами (раньше смешивались с основным Положением под служебными ключами); упоминания «п. 3.4», «пункта 7.2» в тексте — ссылки на этот пункт; у каждого пункта (при наведении) кнопки «скопировать ссылку» и «скопировать текст»; в оглавлении «Раздел N из M» и полоска прогресса чтения, кнопка «наверх»; пока Положение грузится, показываются заглушки; при печати интерфейс скрывается.
* **Лист документа.** Под листом — размеры и размер файла («1200 × 1700 px · 46 КБ · стр. 1 из 2»); страницы листаются кнопками и клавишами `PageUp` / `PageDown`; у кнопок масштаба в подсказках клавиши. У PDF сразу виден настоящий первый лист, а не заглушка.
* **Страница «Статус обращения».** Три этапа (принято → рассматривается → решение) с отметками, пока обращение не рассмотрено, статус обновляется сам раз в минуту (когда вкладка на виду), есть «Обновить» и подпись «проверено N мин назад».
* **История обращения в кабинете.** В карточке обращения — кто и когда его отправил, менял статус, писал ответ и заметку (сами тексты в историю не попадают).
* **Мелочи:** время сообщения при наведении, кнопка «к последнему сообщению», вспышка «красными чернилами» у исправленного поля, «Скопировано» у кнопки копирования, сменяющийся статус в шапке диалога.
* **Верхняя панель** — «остров» из стекла в том же стиле, что на странице сотрудников: знак деканата, плоский переключатель («Стол», «Положение», у вошедшего сотрудника ещё «Сотрудникам»), круглые кнопки поиска `Ctrl+K` и меню (тема оформления, горячие клавиши, «Удалить мои данные», вход для сотрудников). Пока идёт проверка, под названием — этап и процент, вдоль нижнего края идёт тонкая линия прогресса, в заголовке вкладки браузера — «Проверяю… 42%». Граница панели подсвечивается вслед за курсором; на телефоне панель прячется при прокрутке вниз и возвращается при движении вверх. Переходы: `Alt+1/2`.
* **Без технической информации на сайте.** Версии программ, названия движков, «технические подробности» распознавания и внутренние названия вариантов обработки посетителю не показываются, ошибки описаны по-человечески (подробности — только в журнале сервера). Состояние сервиса доступно разработчикам через `GET /api/health` и `python -m dekanat doctor`.

#### Документ не из вуза («другой документ»)

Классификатор умеет говорить «это не мой тип»: приказ, постановление, счёт, договор не подгоняются под справку. В этом случае сервис честно сообщает, что тип не определён, и отвечает **по тексту самого документа**: по нумерованному пункту («Что приказано в п. 1.2?»), по реквизитам шапки («Какая дата документа?», «Какой номер?»), по значению рядом с названием («ИНН», «Итого»), по смыслу («Сколько мешков с песком нужно?») и «О чём документ?». Ответ даётся только из распознанного текста, с рамкой на снимке; нет подходящего места — «ответа нет». Вопросы о правилах (Положение) работают и для таких документов. Режим можно выбрать и вручную — «Другой документ». Рукописный текст (дату и номер, вписанные от руки в шапку) Tesseract читает плохо: на вопрос «какая дата / какой номер документа?» сервис в этом случае честно отвечает, что реквизит не прочитан, и просит сверить со снимком, а не подставляет случайную строку. Белый лист во весь кадр не обрезается по блоку текста: рамка листа ищется только там, где он заметно отличается от фона.

> Набор [MWS-Vision-Bench](https://huggingface.co/datasets/MTSAIR/MWS-Vision-Bench) — это общий бенчмарк OCR/понимания документов, **не** данные кейса (там нет студенческих справок и Положения). Он нужен только для проверки качества распознавания (`scripts/eval_mws_vision.py`); документ из него не обязан попадать в один из трёх типов — и теперь сервис ведёт себя с ним предсказуемо.

Вкладка **«Положение»** — просмотр, поиск и загрузка своего Положения (`.md`, `.txt`, `.docx`, `.pdf`). Раздела для редактирования типов документов в интерфейсе нет: новый тип добавляется YAML-файлом (см. «Описание типа документа»).

### Командная строка

```bash
python -m dekanat ask data/samples/sample_02.png "Хватит ли этой справки для перевода на 2 курс?" --highlight out.png
python -m dekanat ask scan.pdf "Чего не хватает?" --type academic_leave --json

python -m dekanat doctor                           # проверка окружения

```

### Пакетный режим и results.json

Для автопроверки: на вход — список заданий (JSON, JSONL или CSV), на выход — `results.json`.

```bash
python -m dekanat batch --input examples/tasks.json --out results.json --images-dir data/samples
```

Вход распознаёт разные имена колонок: `id`, `image`/`file`/`path`/`file_name`, `question`/`query`, `doc_type`/`type`. Задание без файла — вопрос только по Положению. Ошибка на одном файле не останавливает остальные. Пример результата — `examples/results.example.json`.

Запись результата:

```json
{
  "id": "demo-2", "image": "sample_02.png", "question": "Хватит ли этой справки для перевода на 2 курс?",
  "doc_type": "study_certificate", "doc_type_title": "Справка об обучении",
  "fields": {
    "ФИО студента": "Степанова София Сергеевна", "Название вуза": "Кубанский институт управления и права",
    "Номер и дата выдачи": "номер выдачи: 2172 (не найдено: дата выдачи)", "Подпись и печать (есть/нет)": "нет"
  },
  "answer": "Не хватает даты выдачи и печати вуза. Эти поля обязательны по п. 3.4 Положения.",
  "verdict": "missing", "sources": ["п. 3.4"], "missing": ["даты выдачи", "печати вуза"], "notes": []
}
```

> **Важно про формат.** Точный формат `results.json` описан в README к набору данных организаторов, а его в архиве с ТЗ нет. Формат выше — разумное предположение. Если организаторы требуют другие ключи, меняется одна функция — `result_record()` в [`dekanat/export.py`](dekanat/export.py) (и, при другом формате входных файлов, `read_batch_input()` там же).

### REST API

```bash
curl -F "file=@sample_02.png" -F "question=Хватит ли справки для перевода?" -F "doc_type=auto" http://127.0.0.1:8000/api/analyze
```

Документация OpenAPI — `http://127.0.0.1:8000/api/docs`. Основные методы: `POST /api/analyze` (синхронно, для скриптов), `POST /api/jobs` + `GET|DELETE /api/jobs/{id}` (фоновая задача с прогрессом и отменой — её использует интерфейс), `GET /api/health`, `GET /api/doctypes`, `GET|PUT /api/regulation`, `GET /api/doctypes/{id}/yaml`, `PUT|DELETE /api/doctypes/{id}`, `POST /api/doctypes/validate`. Параметр `doc_type`: `auto`, id типа или `generic` («другой документ»). `PUT /api/regulation` и `PUT|DELETE /api/doctypes/{id}` требуют входа администратора.

Каждый ответ содержит `answer.report`: `conclusion` (вывод), `facts` (факты документа по вопросу), `clauses` и `document_fields` (источники), `missing` и `doubtful` (отсутствующее и сомнительное), `disclaimer` (окончательное решение принимает деканат), а при `USE_LOCAL_LLM=true` — ещё и `explanation`. Поля `answer.text`, `verdict`, `sources` остались как были.

Ассистент (сессия — cookie `dekanat_sid`): `GET /api/assistant/state`, `POST /api/assistant/message` (`defer: true` — вопрос вне анкеты не отвечать, его проверит стол), `POST /api/assistant/document`, `GET|DELETE /api/assistant/document`, `PATCH /api/assistant/document/fields`, `POST /api/assistant/generate`, `GET /api/assistant/download/{id}`, `GET|POST /api/assistant/submission`, `DELETE /api/assistant/data`. Аккаунты (необязательные): `GET /api/account/me`, `POST /api/auth/telegram/start`, `GET /api/auth/telegram/poll`, `POST /api/auth/telegram/webapp`, `POST /api/auth/logout`, `PATCH|DELETE /api/account`, `GET /api/account/tickets|export`, `POST /api/account/tickets/link`, `POST /api/telegram/webhook/{секрет}`. Администратор (cookie `dekanat_admin`): `/api/admin/login|logout|me|password|info|stats|audit|purge|reindex`, `/api/admin/templates…`, `/api/admin/kb…`, `/api/admin/tickets…` — полный список в `/api/docs`.

## Проверка на MWS-Vision-Bench через сайт

`scripts/eval_mws_site.py` отправляет задания датасета (изображение + вопрос) в работающий сервис тем же путём, что и интерфейс (`/api/jobs`), и считает метрики: CER и полноту слов для OCR, попадание эталона для VQA и KIE, IoU для grounding, скорость и надёжность.

```bash
python -m dekanat serve --port 8001
python scripts/eval_mws_site.py run   --root D:/mws-vision-bench --out D:/mws-run --base-url http://127.0.0.1:8001
python scripts/eval_mws_site.py score --root D:/mws-vision-bench --out D:/mws-run     # stats.json и report.md
```

Первый частичный прогон (2213 из 3906 заданий, 204 изображения из 400, только подмножество `business`): распознавание страниц — медиана CER «по окну» 4,5% (у 62% страниц ≤ 10%), в тексте OCR находится ~88% слов эталона; ответы сайта на задания-инструкции («выдай весь текст», «в формате markdown», «верни JSON», «укажи рамку») почти всегда «ответа нет» — это не сценарий кейса (справки и Положение), поэтому датасет проверяет в первую очередь качество OCR. Прогон помог найти и исправить ошибку менеджера задач: долгая задача могла пропасть, пока создавались новые.

## Интерфейс на React

Исходники — в [`frontend/`](frontend/): React 19 + TypeScript (strict) + Vite, тесты — Vitest и Testing Library. Сборка кладётся в `dekanat/web/static/app/` и **закоммичена**, поэтому Python-серверу Node не нужен.

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, запросы /api проксируются на :8000 (запустите python -m dekanat serve)
npm test           # 66 тестов: API-клиент и опрос задач, диалог (useDesk), заключение, карточка полей, выбор типа и документа, «спросить дальше», YAML-помощники
npm run build      # проверка типов + сборка в ../dekanat/web/static/app
```

Устройство: `src/api.ts` — клиент и опрос фоновой задачи с отменой; `src/hooks/useDesk.ts` — диалог (реплики, прогресс, отмена, перезапуск с другим типом); `src/components/desk/` — панель ввода и выбор типа, лента диалога, разбор в реальном времени, заключение со штампом, карточка полей, лоток и просмотрщик снимка (масштаб/щипок/миникарта/луч/рамки); `src/components/` — навигация, палитра команд, панель пункта; `src/views/` — стол, Положение (оглавление со scroll-spy), редактор типов; `src/styles/` — слои CSS, токены и тёмная тема через `light-dark()`. Без сторонних UI-библиотек: анимации — CSS (пружины `linear()`, `@starting-style`) и небольшие хуки. Доступность: семантическая разметка, фокус и клавиатура везде, `aria-live` для статусов, `prefers-reduced-motion` отключает движение; вёрстка подходит для телефона.

Если типы документов у организаторов отличаются от трёх встроенных — опишите их в YAML (см. ниже), код менять не нужно.

## Как это работает

| Модуль | Что делает |
|---|---|
| `dekanat/ocr/preprocess.py` | загрузка JPG/PNG/PDF (EXIF-поворот), поиск листа на фото и перспектива, оценка наклона по строкам текста (до ±45°), выравнивание тени и освещения, стирание линий таблиц, поиск бликов |
| `dekanat/ocr/runner.py` | проходы Tesseract по нескольким вариантам предобработки с остановкой, когда качество достаточно; оценка качества без эталона; OSD для страниц, повёрнутых на 90/180°; увеличение мелкого текста; матрица «исходное фото → обработанное» для подсветки |
| `dekanat/extract/` | поиск названий полей с допуском на опечатки OCR (стемминг + нечёткое сравнение), значение справа/ниже метки, многострочные значения, регулярные выражения для документов «сплошным текстом», запасные детекторы; разбор дат (в т.ч. «О1.О9.2О23»), ФИО, номеров, оценок, периодов |
| `dekanat/extract/marks.py` | подпись и печать **по изображению**: слова «М.П.» и «(подпись)» есть и на пустом бланке, поэтому ищем сами чернила (цветные кольца и пятна, штрихи вне распознанного текста) |
| `dekanat/classify.py` | автоопределение типа документа |
| `dekanat/kb/` | разбор Положения на пункты; BM25 по основам слов + синонимы; **вывод обязательных полей из текста Положения** |
| `dekanat/qa/engine.py` | намерение вопроса (комплектность / значение поля / правила), три вердикта, источники |
| `dekanat/llm/` | `LLMService` (единственная точка доступа к модели), backend Ollama на CPU, промпты, проверка ответов; при `USE_LOCAL_LLM=false` ничего не создаёт и не вызывает |
| `dekanat/dialog/` | конечный автомат диалога, чек-лист анкеты, правила разбора ответов, намерения |
| `dekanat/templates/` | DOCX-шаблоны: проверка файла, плейсхолдеры, заполнение, хранилище версий |
| `dekanat/storage/` | SQLite: сессии, обращения, события статистики, шаблоны, документы базы знаний, журнал; политика хранения |
| `dekanat/admin/` | вход администратора, пароли (scrypt), необязательная блокировка перебора, маршруты `/api/admin/*` |
| `dekanat/kb/manager.py` | документы базы знаний: загрузка, замена, отключение, удаление, переиндексация, история |
| `dekanat/document_processing/` | этапы конвейера «проверка формата» (`formats.py`) и «валидация» (`validation.py`); определение типа и извлечение полей подключены из `classify.py` и `extract/` без дублирования |
| `dekanat/knowledge_base/` | точка входа к поиску по Положению и документам базы знаний (реализация — `dekanat/kb/`) |
| `dekanat/web/` | FastAPI; интерфейс «Стол декана» с анкетой (React, собранный), страница `/admin` без сборки |

### Как выбирается «что обязательно»

Положение читается как данные, а не зашивается в код. Пункт относится к типу документа, если называет его (или стоит в разделе с таким названием). Поле «требуется» пунктом, если пункт его называет и сформулирован обязывающе. Сила формулировки: «обязательны», «не принимается» → «должна содержать», «необходимо» → «указываются». Для поля берётся пункт с самой сильной формулировкой, поэтому недостающие дата и печать ссылаются на п. 3.4 («обязательными реквизитами… не принимается»), а не на перечень в п. 3.2; если всё на месте — называется пункт-перечень (п. 3.2). Если Положение вообще не называет требований к типу документа, используется `required_fallback` из конфига, и ответ прямо об этом сообщает.

### Как формируется ответ

* **Проверка комплектности** («хватит ли…», «подойдёт ли…», «чего не хватает…», пустой вопрос): недостающие поля сгруппированы по пунктам. Если вопрос про цель, для которой Положение называет *другой* документ, ответ об этом скажет.
* **Значение поля** («какая форма обучения указана?», «кто руководитель практики?»): значение из карточки + поле-источник. Поле не найдено, но обязательно → вердикт «не хватает» с пунктом.
* **Правила** («за какой срок рассматривается заявление?»): ближайший пункт Положения, дословно, с номером.
* **Нет данных**: если слова вопроса не покрываются ни одним пунктом (а «редкие» слова вроде «стоит», «стипендия», «общежитие» не найдены вовсе), ответ — «нет информации». Слова-уточнения («максимальный срок») отказ не вызывают.
* Опционально (`USE_LOCAL_LLM=true`): на пограничных вопросах локальная модель решает *только* «есть ли ответ в этих пунктах и в каком» (номер пункта принимается только из найденных). Текст ответа всё равно берётся из Положения. Модель не обязательна: без неё сервис просто осторожнее (чаще «ответа нет»).
* Каждый ответ дополнительно раскладывается в `answer.report` (вывод, факты, пункты, отсутствующее и сомнительное, оговорка о решении деканата) — см. «REST API».

## Настройка

`config/settings.yaml` — все параметры с комментариями; любой можно переопределить переменной окружения `DEKANAT_<РАЗДЕЛ>_<КЛЮЧ>` (например, `DEKANAT_OCR_TESSERACT_CMD`, `DEKANAT_LLM_MODEL=qwen2.5:3b-instruct`, `DEKANAT_SERVER_PORT=9000`). Включение модели — короткая переменная `USE_LOCAL_LLM=true`. Новые разделы: `llm` (модель и CPU-параметры), `storage` (БД, шаблоны, готовые документы), `privacy` (сроки хранения), `admin` (правила входа), `delivery` (канал обращений); `ocr.cache_size` — кеш OCR в памяти.

Для лучшей точности OCR можно подложить данные `tessdata_best` (rus, eng, osd) в отдельную папку и указать её в `ocr.tessdata_dir` — это самый простой способ улучшить чтение сложных снимков.

### Описание типа документа (YAML)

Минимальный пример (полные — в `config/doc_types/`):

```yaml
id: scholarship_certificate           # латиница, строчные, цифры, «_»
title: Справка о стипендии
short_title: Справка                  # «Справка содержит все данные…»
genitive: справки о стипендии
aliases: [справка о стипендии]        # как документ называют в Положении (для привязки пунктов)
classify:                             # автоопределение типа
  keywords:
    - {phrase: справка о стипендии, weight: 7}
  negative:
    - {phrase: академический отпуск, weight: 5}
fields:
  - id: student_name
    title: ФИО студента               # название в карточке и в results.json
    kind: person
    labels: [ФИО студента, ФИО, Студент]            # как поле подписано в документе
    mention: [ФИО студента]                          # как поле называется в Положении (по умолчанию — title и многословные labels)
    patterns: ['(?i:студент(?:ка)?)\s+(?P<value>{FIO})']   # для текста «сплошным абзацем»; макросы {DATE} {FIO} {NUM}
    missing_phrase: ФИО студента      # «Не хватает …» (родительный падеж)
  - id: amount
    title: Размер стипендии
    kind: number
    labels: [Размер стипендии, Сумма]
    missing_phrase: размера стипендии
```

Виды полей (`kind`): `person`, `org`, `text`, `date`, `number`, `choice` (нужен `choices`), `period`, `grade`, `group`, `course`, `composite` (части в `parts`, например «Номер и дата выдачи»), `marks` (подпись/печать, части с `mark: signature | stamp`). Дополнительно: `multiline: true`, `fallback: header_org | unclaimed_date_last`, `format` для составных, `export_title`, `checks` (проверка порядка дат), `required_fallback`.

Проверка конфига: `python -m dekanat validate-config`. Файл кладётся в `config/doc_types/`, тип подхватывается при запуске; для работающего сервера есть REST-интерфейс администратора (`POST /api/doctypes/validate`, `PUT /api/doctypes/{id}`) — применяется сразу, без перезапуска. Тест `tests/test_new_doctype.py` показывает полный путь: новый тип + пункты Положения + документ → корректный ответ без правок кода.

## Качество и оценка

Данных организаторов в архиве нет, поэтому качество проверялось на **синтетических документах**, которые генерирует сам проект (`python -m dekanat synth`): три типа документов × три вёрстки (форма, таблица, сплошной текст), шрифты, рукописная подпись и круглая/прямоугольная печать, «дефекты» (нет даты, номера, подписи, печати…) и три уровня порчи: 0 — чистый скан, 1 — лёгкое фото, 2 — тяжёлое фото (наклон до 30°, тень, блик, перспектива, ≈900 px по ширине, JPEG q45–70).

```bash
python -m dekanat synth --out data/synthetic --n 6 --levels 0,1,2 --seed 101   # документы + эталон + вопросы
python -m dekanat eval --data data/synthetic --verbose                          # полный путь, как у автопроверки
python -m dekanat eval --data data/synthetic --oracle                           # только логика ответов (OCR не нужен)
```

Результат на **свежем наборе** (seed 101: 54 документа, 146 вопросов), который не использовался при настройке; ноутбук без GPU, ≈1–3 с на страницу:

| Метрика | Чистые сканы | Лёгкие фото | Тяжёлые фото | Всего |
|---|---|---|---|---|
| Тип документа (автоопределение) | 18/18 | 18/18 | 18/18 | **100 %** |
| Поля карточки (допуск ≤10 % на опечатки OCR) | 98,7 % | 98,1 % | 85,3 % | **94,0 %** (строго — 92,1 %) |
| Подпись и печать (есть/нет) | — | — | — | 95,6 % (86/90) |
| Вердикт ответа (в порядке / не хватает / нет ответа) | 97,8 % | 100 % | 90,6 % | **95,9 %** (140/146) |
| Ссылка на верный пункт Положения | 96,2 % | 100 % | 96,4 % | **97,4 %** (76/78) |

По видам вопросов: правила — 24/24, «ответа нет» — 16/16, значение поля — 49/52, комплектность — 51/54. Точное совпадение *списка* недостающих полей — 72 % (21/29): на тяжёлых фото OCR иногда «теряет» ещё и соседние поля.

**Повторная проверка после добавления гибридных функций.** Набор seed 101 был сгенерирован заново в другом окружении (Python 3.14, Pillow 12.3, Tesseract 5.4); картинки получились не побайтно такими же, как у авторов таблицы выше, поэтому цифры немного ниже: поля (допуск ≤10 %) 428/468 = 91,5 %, строго 420/468 = 89,7 %; вердикт 137/146 = 93,8 % (чистые сканы 97,8 %, лёгкие фото 100 %, тяжёлые 84,9 %); верный пункт Положения 77/78 = 98,7 %; точный список недостающих полей 20/29. Чтобы исключить регрессию, **тот же набор прогнан на исходном коде до изменений** (коммит `2172359`) — результаты совпали до единицы. Таблица выше оставлена как исторические значения авторов; сравнивать «до/после» нужно по паре прогонов на одном наборе.

Отдельно проверялась логика ответов на **разговорных формулировках** (`tests/test_qa_heldout.py`). На первом честном прогоне свежего набора из 26 разнообразных, местами намеренно каверзных вопросов («Справка полная?», «Мне могут отказать из-за справки?», «До какого числа действует справка?») результат был **50 %** (13/26). Разобрав ошибки, я исправил общие лексические пробелы (синонимы, обороты), после чего эти вопросы стали регрессионными тестами — их 98 % уже не «независимая» оценка. Реалистичный ориентир для действительно незнакомых формулировок — ближе к первым 50–75 %: подход лексический, а не семантический.

**Оговорки.** (1) Синтетические документы нарисованы тем же проектом, на котором настраивались эвристики: на реальных данных организаторов цифры будут ниже, особенно для подписи/печати и нестандартных вёрсток. (2) Вопросы в наборе составлены из тех же пулов формулировок, что и в разработке — поэтому метрики ответов выше, чем на разговорной речи (см. абзац выше). (3) Самое слабое звено — тяжёлые фото низкого разрешения: текст там нередко физически нечитаем. (4) Данных организаторов (документов, Положения, вопросов) в архиве с ТЗ нет — на них проект не запускался.

### MWS-Vision-Bench

[MWS-Vision-Bench](https://huggingface.co/datasets/MTSAIR/MWS-Vision-Bench) — общий бенчмарк русскоязычных бизнес-документов для мультимодальных моделей (сканы, таблицы, рукописные документы; задания: парсинг документа, OCR страницы, извлечение ключевой информации, VQA, привязка текста). Справок и Положения вуза в нём нет, поэтому он **не заменяет** данные организаторов, но подходит для проверки звена OCR на документах разного качества. Скрипт `scripts/eval_mws_vision.py` считает CER «полного пайплайна» против «голого» Tesseract на заданиях «full-page OCR»; датасет (≈820 МБ) в репозиторий не входит и сам не скачивается — только по явному `--download N`:

```bash
python scripts/eval_mws_vision.py --root data/mws --download 15 --limit 15      # скачает metadata.jsonl и 15 изображений
python scripts/eval_mws_vision.py --root D:/datasets/MWS-Vision-Bench --limit 30 # локальная копия
```

## Ограничения (честно)

* **Чёрно-белые сканы.** Печать на сером скане находится (по форме кольца), а подпись нет: у неё нет цвета, и её штрихи нельзя отделить от кольца печати. Поэтому справка, в цвете признанная «в порядке», в чёрно-белом скане получает «не хватает: подпись не обнаружена». Ответ честный, решение за сотрудником; поведение зафиксировано тестом `test_grayscale_scan_known_limitation`.
* **Формат данных и `results.json` организаторов неизвестен** — см. выше, что менять.
* **OCR — только Tesseract** (в установленной здесь версии файл `rus.traineddata` занимает около 4 МБ — это компактная модель; `tessdata_best` обычно точнее). EasyOCR/PaddleOCR не подключены: интерфейс движка (`OcrRunner` ↔ `TesseractEngine`) простой, но других движков в проекте нет. Типичные ошибки: путаница «Э»/«3», «Ф»/«0» в кодах групп (код при этом считается найденным), потеря символов на нечитаемых снимках.
* **Подпись и печать — эвристика по изображению.** Подпись поверх печати того же цвета может не найтись; крупный нераспознанный печатный текст у линии подписи иногда похож на подпись. У каждой находки есть уверенность и рамка.
* Срок действия справки («действительна 30 дней») **намеренно не проверяется** — для этого нужна дата «сегодня», а результат зависел бы от дня проверки.
* Положение читается как «пункты текста»: сложные таблицы, примечания и ссылки между пунктами не разбираются. В `.docx` автонумерация Word восстанавливается приблизительно.
* Telegram-бот и Mini App есть, но выключены по умолчанию и не проверялись с живым Telegram (см. «Telegram и требования ТЗ»).
* **Безопасность рассчитана на локальный запуск или закрытую сеть.** Есть вход администратора, проверка `Origin` и (по желанию) блокировка перебора, но нет HTTPS (его даёт обратный прокси; для https выставьте `server.cookie_secure: true`), двухфакторного входа, ролей кроме «администратор» и ограничения частоты запросов пользователей. Не публикуйте сервис в интернет без прокси и `admin.protect_edit: true`. Блокировка входа (если включена) хранится в памяти процесса и сбрасывается при перезапуске.
* **Ограничения запросов минимальны:** с одного адреса можно открыть не более `server.max_new_sessions_per_minute` (60) новых сессий в минуту; частота сообщений и загрузок внутри сессии не ограничена (OCR идёт не более чем в два потока).
* **Без входа пользователи не аутентифицируются:** сессия — это только cookie браузера. Кто завладел cookie, видит данные сессии; сменить устройство и сохранить анкету без входа нельзя (данные живут `privacy.session_ttl_hours`). Вход через Telegram (необязательный) решает это для тех, кто его включил.
* **Локальная модель — необязательное дополнение, её качество не измерялось.** Qwen2.5-3B-Instruct в проекте проверена только через подменяемый интерфейс (модульные тесты); с настоящей моделью автоматически проверялась лишь связка с Ollama на `llama3.1:8b` (структура и безопасность ответов, а не точность). Скорость на CPU зависит от машины и не обещается. Метрики раздела «Качество и оценка» получены **без** модели.
* **Анкета и DOCX.** Анкета поддерживает перевод и зачисление; заявление на академический отпуск она не оформляет (его документ только проверяется). Паспортные данные принимаются только в формате РФ (серия 4 + номер 6 цифр) — иначе поле нужно пропустить и вписать вручную. Таблицы и надписи заполняются, но поля формы Word (content controls), колонтитулы «как в предыдущем разделе» и текст внутри `w:fldSimple` не обрабатываются. Шаблон проверяется на безопасность, но не на соответствие какому-либо официальному бланку.
* **Отправка в деканат** — только внутренняя очередь (письмо с кодом студенту по SMTP — необязательное и выключенное по умолчанию; интеграции с СЭД нет). Вошедший через Telegram получает уведомления об ответе деканата в чат; остальные смотрят статус сами на странице «Статус обращения».
* **База знаний** индексирует текст документов лексически (BM25), векторного поиска нет. PDF без текстового слоя (сканы) в базу знаний не принимаются — для них нужна текстовая версия. Пункты дополнительных документов участвуют в выводе «что обязательно для документа» наравне с основным Положением — загружайте только действующие регламенты.
* Docker-образ по-прежнему не собирался в среде разработки.

## Использованные инструменты

Tesseract OCR 5 (языки rus, eng, osd) · OpenCV · NumPy · Pillow · pypdfium2 · PyYAML · snowballstemmer · RapidFuzz · FastAPI + Uvicorn · python-multipart (загрузка файлов) · python-docx (DOCX-шаблоны) · httpx (клиент Telegram Bot API, только если бот включён) · SQLite и `hashlib.scrypt` из стандартной библиотеки (хранилище, пароли) · Ollama + Qwen2.5-3B-Instruct (необязательно, локально, CPU; интеграция проверена на установленной `llama3.1:8b`). Интерфейс: React 19 + TypeScript, сборка Vite (собранная версия лежит в `dekanat/web/static/app/`, Node.js нужен только для пересборки); страница сотрудников — HTML, CSS и JavaScript без сборки. Тесты: pytest + httpx (TestClient), Vitest + Testing Library + jsdom. Внешние API (GigaChat, YandexGPT и т. п.) **не используются**. Вычисления — CPU ноутбука (Intel Core 7 150U, 16 ГБ ОЗУ, без GPU).
